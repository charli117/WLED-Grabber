Audit findings
  1. §5.2.2 row 1 over-claimed ImageLifecycle, GenerationGate and WledSetupController
     as production-wired. They remain test/helper-only; WledScreenService implements
     the equivalent close/generation logic inline. Documentation corrected.
  2. BootActivity now performs one fresh HTTP probe and a DeviceReadiness evaluation
     against the stored StartConfirmation before requesting system consent. A failed
     or missing verification keeps the boot reminder and closes without consent.
     The reminder/manual entry opens StartCaptureActivity. Instrumentation covers the
     rejection paths only: a successful probe -> system consent path needs a real
     WLED or a loopback-allowed endpoint (WledHttpClient rejects loopback by default).
  3. CAP-2 remains 待验证: implementation exists, but no active-projection API34
     resize/single-app-window or 100-cycle rotation evidence.
  4. Residual CAP gap: UdpDatagramSink's constructor calls InetAddress.getByName on
     the service main thread. IP literals avoid DNS; a hostname configuration can
     still resolve on the main thread, so CAP-1's "main-thread network calls = 0"
     criterion is not fully satisfied. Not changed in this audit (CRITICAL graph
     impact; needs a dedicated pre-resolution design).
  5. CAP-3 remains 已验收 on its own ownership/race evidence, while its prerequisite
     CAP-2 is 待验证. This is recorded as a status-consistency note; no transitive
     downgrade is applied because the cards use evidence-level acceptance.
  6. Stop-budget residual: WledSession.release runs turnOff + readState sequentially
     (each up to the 3 s app deadline) while LedStreamer.stop waits 3 s. Under a slow
     network the writer thread can exceed 3 s; the main thread returns within 3 s and
     reports UNCONFIRMED truthfully, but the "3 s total stop budget" is a wait bound,
     not a hard deadline. Not changed in this audit.
